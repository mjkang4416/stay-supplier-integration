### 4.7 연동 지표·모니터링

구현 상태: 지표 수집은 구현 예정, 알림 규칙과 한도 탐색 절차는 설계만.

**지표** (Micrometer, 어댑터 호출 지점에서 기록, Actuator `/actuator/metrics`로 노출)

| 지표 | 타입 | 태그 |
|---|---|---|
| `supplier.request` | counter | `supplier`(A/B), `result`(success / timeout / rate_limited / error / invalid_response) |
| `supplier.request.duration` | timer (p50/p95/p99) | `supplier` |
| `search.partial_failure` | counter | 실패한 공급사 |

성공률 = success / 전체, 타임아웃 비율 = timeout / 전체, 429 비율 = rate_limited / 전체로 계산한다.

**알림 규칙** (메트릭 모니터. 임계치는 보수적으로 시작해 관측으로 조정)

| 조건 (5분 창) | 수준 | 의미 |
|---|---|---|
| 429 1건 이상 | 알림 | 호출 한도에 닿기 시작. 허용 속도·배분 조정 신호 |
| 429 비율 > 1% 또는 부분 실패 비율 > 5% | 긴급 | 고객 검색 결과가 실제로 줄고 있음 |
| 공급사 성공률 < 97% 또는 타임아웃 비율 > 2% | 긴급 | 공급사 장애 또는 타임아웃 값 부적절 |
| p95 지연 > 응답 타임아웃의 80% | 알림 | 타임아웃 임박. 값 재검토 |

**호출 한도 탐색 절차** (한도 값을 모르는 상태에서 안전하게 찾기)
1. 허용 속도 설정값을 보수적으로 시작한다(예: 초당 2회).
2. 429 알림이 일정 기간(예: 수 일) 없으면 20%씩 올린다.
3. 429가 나오면 코드가 자동으로 절반으로 줄이고(AIMD), 알림을 받은 사람은 직전 안정값의 80%를 설정에 기록한다.
4. 찾은 값은 설정으로 고정하고, 이후에는 429 비율 모니터로 이탈만 감시한다.

**역할 구분**: 비율·추세·임계치는 메트릭 모니터(예: Datadog), 정규화 실패·예상 못 한 예외처럼 한 건이라도 조사해야 하는 것은 예외 추적(예: Sentry)에 보낸다. 429는 정상 운영 상황이므로 예외로 보내지 않는다. 429 모니터의 알림은 허용 속도 조정(위 절차)과 공유 캐시 도입(4.8 전환 조건)의 판단 신호로 쓴다.

### 4.8 요금·재고 캐시 (선택, 설계만)

구현 상태: 설계만. 필수 흐름은 캐시 없이 검색마다 재고·요금 API를 호출한다. 검토 과정은 [JOURNAL](../JOURNAL.md)의 "요금/재고 캐시" 항목에 있다.

요구사항과의 관계: 요금·재고를 DB에 쌓지 않는다는 요구는 지킨다(캐시는 TTL이 있는 휘발성 저장이고 원본은 공급사). 캐시 전략은 선택 구현(§3.3)으로 명시된 항목이다. 다만 캐시를 붙이더라도 필수인 연동 견고성(병렬 호출·타임아웃·부분 실패·실패 판정 통일)은 갱신 잡의 호출 경로와 캐시 미스 경로에서 그대로 동작해야 하며, 캐시가 그 동작을 가리면 안 된다.

**목표 구조와 전환 조건.** 인스턴스가 여러 대인 운영 환경의 목표 구조는 관리형 Redis(예: ElastiCache) 공유 캐시다. 인스턴스별 인메모리 캐시는 인스턴스마다 값이 달라지고 호출 절감 효과가 인스턴스 수만큼 희석되므로 택하지 않는다. 도입 시점은 4.7의 메트릭 모니터가 정한다. 429 알림이 반복되거나 검색 QPS × 인스턴스 수 × 공급사별 묶음 수가 허용 호출 속도에 근접하면 도입한다. 그 전까지는 호출 최적화(요청당 50개 채우기, A는 긴 기간 한 번 호출, 인스턴스 안 동시 요청 병합)로 대응한다.

**모델: 주기 갱신형 저장소.** Redis에 정규화된 표준 모델을 날짜별로 펼쳐 올려 두고 갱신 잡이 값을 바꾼다. 검색은 어떤 날짜 범위·인원이든 Redis 값을 조립해서 응답하고, 캐시 범위 안에서는 공급사를 직접 호출하지 않는다.

```
Redis Hash  키: stay:v1:{hotelId}
            필드: {roomTypeId}:{date} → { remainingRooms, nightlyRate, taxAmount, currency, breakfastIncluded }
            날짜 창: 오늘 ~ +30일

[갱신 잡]   계층별 주기로 재고·요금 API 호출(adults=1로 모든 객실 타입 수집) → 정규화 → 필드 갱신.
            직전 값과 비교해 변경 여부 기록
[매일 새벽] 매핑 델타 반영(비활성 숙소 키 삭제, 새 숙소 추가), 지난 날짜 필드 HDEL, 날짜 창 전진
[검색]      숙소마다 HMGET {roomTypeId}:{date} × 숙박일 (파이프라인)
            객실 타입마다 예약 가능 객실 수 = min(remainingRooms), 요금 = Σ(nightlyRate + taxAmount)
            maxOccupancy ≥ adults + children 인 객실 타입만 남김 → 병합 → 응답
[예약 직전] 캐시를 쓰지 않고 실시간 재확인
```

인원 축을 캐시 키에서 뺀 근거: 스펙상 요금은 객실 타입·날짜별이고 인원은 수용 가능 객실 타입을 거르는 조건으로만 작용한다. `adults=1`로 호출하면 모든 객실 타입이 오므로, 필터는 검색 시 우리가 한다. 실제 공급사가 인원별 요금을 쓰면 인원 축을 키에 다시 넣어야 한다.

| 항목 | 설계 |
|---|---|
| 캐시가 성립하는 조건 | 같은 키에 대한 검색이 변경보다 잦을 때. 키(객실 타입·날짜) 하나의 변경 간격은 요금 30분~2시간(RMS 제품 사양, 대리 지표), 재고 1.6~5시간(점유율·숙박일수·리드타임 역산). 재고 갱신 소프트웨어의 기술 상한(PMS API property당 초당 5회, Cloudbeds 공식 문서)은 실제보다 세 자릿수 위라 근거로 쓰지 않음. 인기 키의 검색은 분당 단위라 성립. 실측 데이터는 공개된 것이 없어 우리 시스템의 변경 감지율로 대체 |
| 저장소 | Redis (인스턴스 간 공유, 공급사 호출 한도 429 대응) |
| 키·자료구조 | 숙소당 Hash 하나 `stay:v1:{hotelId}`. 키 수가 숙소 수와 같아 키 오버헤드가 작다. 필드 `{roomTypeId}:{yyyyMMdd}` (예 `11:20260901`). 날짜 범위 검색은 HMGET 한 번. 접두사 버전은 표준 모델 변경 배포 시 올림 |
| 값 | 정규화한 값을 구분자 문자열로 저장: `재고\|요금\|세금\|통화\|조식\|기준` (예 `3\|120000\|12000\|KRW\|0\|n`, 기준 n=세금 별도, g=세금 포함). JSON(약 120B) 대신 약 25B로 두어 필드 값 64B 이하·필드 128개 이하 조건을 만족시키면 Redis가 Hash를 listpack으로 압축 저장한다(객실 타입 4개 × 30일 = 120필드). 공급사 원본은 저장하지 않는다 |
| 메모리 추정 | listpack 유지 시 숙소당 약 6~8KB. 2,000개 ≈ 15MB, 10,000개 ≈ 80MB, 50,000개 ≈ 400MB. JSON 값이면 listpack이 풀려 3~5배 |
| 날짜 창 밖 검색 | 커버리지 정책으로 결정: 창을 넓히거나(호출 예산과 교환) 그때만 직접 호출. 캐시 구조와는 별개 |
| 갱신 주기 (출발값) | D-0~D-3: 5분 / D-4~D-14: 15분 / D-15~D-30: 60분. 키 단위 변경 간격 중 짧은 쪽(요금 30분)에 허용 오차 약 15%를 적용해 임박 5분으로 두고, 먼 날짜는 변경·검색이 모두 드물어 늘림. 같은 계층 안에서는 최근 검색이 많은 숙소부터 |
| 갱신 주기 조정 | 갱신 시 값이 바뀐 비율(변경 감지율)을 공급사·날짜 거리별로 기록. 5% 미만이면 주기를 늘리고(낭비), 30% 초과면 줄이거나 예산을 올림(옛 값 노출). 공개 통계는 출발값에만 쓰고 실측이 최종 근거 |
| TTL | 갱신 주기의 3배. 만료 장치가 아니라 갱신 잡이 멈췄을 때 옛 값이 남지 않게 하는 안전장치 |
| 호출 예산 | 병목은 Redis가 아니라 공급사 호출 한도. 갱신 잡은 토큰 버킷으로 허용 속도의 일부(예: 60%)만 쓰고 나머지는 실시간 검색용. 호출 1회 결과(숙소 최대 50개)는 파이프라인으로 한 번에 저장 |
| 허용 속도 | 스펙에는 요청당 50개 상한과 429의 존재만 있고 초당 호출 한도는 없다. 설정값으로 두고 보수적 기본값(초당 2회)에서 시작해, 429를 받으면 속도를 절반으로 줄이고 일정 시간 429가 없으면 조금씩 올린다(AIMD). `Retry-After` 헤더가 있으면 존중 |
| 예산 검산 (숙소 1,000개, B 기준, 분당 72회 예산) | D-0~3: 20묶음 × 4일 = 80회/5분 = 16/분, D-4~14: 220회/15분 = 15/분, D-15~30: 320회/60분 = 5/분 → 합계 36/분. 숙소 5,000개면 5배라 먼 계층 주기를 늘리거나 예산 상향 |
| 공급사별 채우기 | A: 묶음(50개)당 체크인=오늘·체크아웃=+30일·adults=1 한 번 호출로 `dailyRates` 30일치를 채움. 날짜별 값과 연박 합산이 스펙 정의와 같음. B: 기간 총액만 주므로 묶음당 날짜마다 1박 호출(30회)로 채우고, 연박 요금은 1박 값의 합으로 근사한다. 연박 할인 등이 있으면 실제와 다를 수 있으므로 예약 직전 재확인으로 보정하고 문서에 명시 |
| 변동성 높은 숙소 | 변경 감지율이 특히 높은 숙소는 별도 계층으로 빼서 주기를 줄이거나 캐시에서 제외 |
| 스탬피드 | 키 집합 밖 조합의 동시 요청은 한 요청만 호출(single-flight), 나머지는 대기 |
| Supplier B 주의 | 기간 총액만 주므로 날짜별 저장으로 연박 요금을 재구성할 수 없다. 키는 날짜 범위 단위 |
| 설정값 | 허용 속도, 배분 비율, 날짜 창, 계층별 주기는 설정으로 두고 변경 감지율·429 발생률을 보며 조정 |

## 5. Mock Supplier

공급사 A·B의 API를 흉내 내는 별도 모듈. 채점 대상이 아니라 연동 동작을 검증하는 수단이므로 최소로 구현한다.

### 5.1 실행
```bash
./gradlew :mock-supplier:bootRun   # 포트 9090
```

### 5.2 엔드포인트

| 엔드포인트 | 역할 | 모드 적용 |
|---|---|---|
| `GET /a/v1/hotels` | Supplier A 숙소 목록 | 없음 |
| `GET /a/v1/availability?hotelCodes=...` | Supplier A 재고·요금 | 있음 |
| `GET /b/api/properties` | Supplier B 숙소 목록 | 없음 |
| `GET /b/api/search?propertyIds=...` | Supplier B 재고·요금 | 있음 |
| `POST /control/{a\|b}/mode?value=...` | 공급사별 모드 전환 | - |

- 응답 본문은 `src/main/resources/responses/*.json`의 고정 데이터이며 요청 파라미터는 무시한다.
- 요청 파라미터 필터링, 요청당 숙소 수 상한 초과 오류, 응답 지연 모드, 숙소 목록 API 장애 모드는 필요해지면 추가한다.

### 5.3 모드

| 모드 | Supplier A 재고·요금 응답 | Supplier B 재고·요금 응답 |
|---|---|---|
| `normal` (기본) | HTTP 200 + 정상 본문 | HTTP 200 + `resultCode: "0000"` |
| `error` | HTTP 503 + `{"error":"SERVICE_UNAVAILABLE"}` | HTTP 200 + `{"resultCode":"E503","data":null}` |
| `no-response` | 응답을 보내지 않고 10분 대기 | 같음 |

```bash
curl -X POST 'http://localhost:9090/control/a/mode?value=error'         # A 장애
curl -X POST 'http://localhost:9090/control/b/mode?value=no-response'   # B 무응답
curl -X POST 'http://localhost:9090/control/a/mode?value=normal'        # A 복구
```

### 5.4 구성 방식 선택
별도 모듈로 둔다. WireMock 독립 실행은 코드가 없는 대신 매핑 문법과 시나리오 상태 API를 익혀야 하고 공급사별 모드 전환이 복잡하다. 본 앱 안의 테스트용 컨트롤러는 같은 프로세스에서 자기 자신을 호출해 스레드가 묶이고, 분리하려면 앱을 두 번 띄우면서 본 앱 로직을 꺼야 한다. 자동 테스트에서는 이 모듈에 의존하지 않고 WireMock을 테스트 안에서 띄운다 (7장).
